# spec-review：確定前の独立レビュー

## 目的
同じ会話の中で作った成果物を同じ会話の中で評価すると、作成者の意図や会話の流れに引っ張られて評価が甘くなる（迎合・自己正当化）。
このスキルは、成果物を経緯を知らない独立したレビュアーに渡し、「次のフェーズに進めてよいか」を判定させる。

目標は「すべての問題を拾う」ことではなく、「手戻りが高くつく問題を確定前に拾う」こと。

## いつ使うか

### cc-sdd を使うリポジトリ（通常は /issue から呼ばれる）
| タイミング | 対象 | 必須度 |
|---|---|---|
| 既存の Issue から始めるとき（/issue のフェーズ0-A） | Issue 本文とコメント | 必須 |
| Discovery 後、方向を決める前 | 複数の選択肢がある場合のみ。「比較モード」で評価する | 任意 |
| `/kiro-spec-requirements` 後、承認前 | requirements.md | 必須 |
| `/kiro-spec-design` 後、承認前 | design.md（requirements.md を参照資料として渡す） | 必須 |
| `/kiro-spec-tasks` 後、承認前 | tasks.md（design.md を参照資料として渡す） | 必須。ただし分割せず1回、観点は「設計の要素がタスクに漏れなく落ちているか」を中心にする（`/kiro-spec-tasks` 自体もタスク構成の妥当性チェックを行うため） |
| 実装後 | 対象外。`kiro-review` / `/kiro-validate-impl` / `/code-review` を使う | — |

cc-sdd 自体にもレビュー（requirements-review-gate、`/kiro-validate-design` など）はあるが、どれも作成者が同じ文脈で行うセルフチェックで、`/kiro-validate-design` は会話の経緯を参照する手順になっている。spec-review はこれを置き換えるものではなく、承認の直前に独立した視点を足すもの。

### cc-sdd 以外
要件・設計・方針を確定する直前。特に、データ構造、外部とのインターフェース・API、アーキテクチャ、外部との約束など、後から戻しにくい判断の前。

### 使わなくてよいもの
文言の細部、後から簡単に直せる変更、1ファイルで閉じる小さな修正。

## 手順

### 1. レビュー用の資料を作る（バイアスを持ち込まない）
最初に、対象の成果物のハッシュ（`git hash-object <ファイル>`）を計算して控えておく。記録に残すのはこの値。レビュー中に成果物が変わっても、後の照合で検知できるようにするため。

渡すもの：
- 対象の成果物。要約せず、ファイルパスか本文をそのまま渡す
- 前提：目的、制約、対象外とする範囲。Issue 本文の該当部分（なければ brief.md）を要約せずにそのまま貼る。作成者が書き直すと、都合のよい切り取りが入り得るため
- 参照用の上流成果物（設計レビューなら requirements.md など）
- ユーザーの決定事項（cc-sdd の場合）：`clarifications.md` のうち、状態が「回答済み」「反映済み」の項目の「質問」と「回答（原文）」だけを、そのまま貼る。示した選択肢の説明、推奨、「決定」欄は渡さない（作成者の解釈と判断理由が入るため）

渡さないもの：
- 会話の経緯や議論の過程
- 誰が提案したか、ユーザーがどの案を推しているか
- 「よくできていると思う」「ここは問題ないはず」といった評価や期待
- 過去のレビュー結果。ただし再レビューのときだけは、前回の指摘を「解消されたかの確認対象」として渡してよい
- 作成者の判断理由が書かれたファイル：`.kiro/specs/<feature>/reviews/`、`research.md`、`clarifications.md` 本体。依頼文で「読まないこと」と明記する

### 2. 範囲が広ければ分割する（二軸）
目安：要件エリアが5つを超える場合、または対象が約300行を超える場合。
- **縦の分割**：要件エリア・モジュールごとに個別にレビューする
- **横の1回**：全体を通して、要件同士・セクション同士の矛盾と依存関係だけを見るレビューを1回行う

縦の分割だけだと境界をまたぐ矛盾が拾えなくなるため、横の1回は省略しない。

### 3. 観点を指定する
指定しないと、レビューが目につきやすい観点に偏る。
- **Issue**：目的の明確さ、範囲（やる・やらない）、完了条件が検証できるか、リポジトリの現状との食い違い（既に実装済み、前提の機能がない、技術的に成り立たない）、ほかの Issue との重複・衝突、1つの Spec に収まる大きさか、Spec を書くのに足りない情報。レビュアーにはリポジトリのコードと README・steering を読ませ、前提には Issue 本文ではなく README・steering の該当部分を渡す。結果は `.kiro/specs/` ではなく /issue の報告として示す（Spec がまだないため）
- **要件**：目的との整合、抜け漏れ（主要な利用シナリオ・エラー時・境界条件）、要件同士の矛盾、検証できる書き方になっているか、対象範囲の境界の明確さ、暗黙の前提
- **設計**：要件を満たしているか（要件ごとの対応）、データ構造・インターフェースの妥当性（戻しにくい部分を優先）、エラー処理・異常系、非機能（性能・セキュリティ・運用）、既存コードとの整合、より単純な代替案の有無
- **要件・設計に共通**：ユーザーの決定事項が成果物に反映されているか。前提・参照資料・決定事項に根拠のない決定（作成者の推測）が含まれていないか
- **タスク**：設計の全要素がタスクに落ちているか、順序と依存関係、各タスクの完了条件の明確さ、粒度

### 4. 独立した文脈で実行する
- **Claude Code の場合**：Agent ツールで general-purpose のサブエージェントを起動し、手順1の資料だけを渡す。会話を引き継ぐ fork は使わない（独立性がなくなる）。分割した場合は並列に起動してよい。設計レビューでは、既存コードとの整合を見るために、サブエージェントがリポジトリのコードを読むことは許可する。
- **claude.ai のチャットの場合**：下の依頼文に資料を埋め込んで出力し、ユーザーに「新しいチャットに貼ってください（可能ならそのチャットはメモリをオフにして）」と伝える。

### 5. 依頼文（中立な聞き方）
「欠陥を探して」とは頼まない。欠陥がある前提で探し、問題を水増しするため。「進めてよいか判定して」と頼む。

```
あなたはこの成果物を初めて見るレビュアーです。以下の成果物で次のフェーズ（{次のフェーズ}）に進めてよいかを判定してください。

## 前提
{目的・制約・対象外を数行}

## ユーザーの決定事項
{質問と回答の原文。なければ省略}
これらは前提として扱ってください。ただし、決定同士や前提との矛盾、決定がもたらす大きなリスクがあれば、「決定事項への懸念」として指摘してかまいません。

## 見てほしい観点
{手順3の観点}

## 成果物
{成果物の本文、またはファイルパス}

## 参照資料
{上流成果物。なければ省略}

## 読まないもの
リポジトリ内のファイルを読んでよいが、`.kiro/specs/<feature>/reviews/`、`research.md`、`clarifications.md` は読まないこと（作成者の判断理由が書かれており、先入観になるため。必要な決定事項は上に貼ってある）。

## 出力形式
- 判定：GO / 条件付きGO / NO-GO と、その理由を1〜2文
- 指摘：各項目に重要度（致命的／要検討／好みの問題）、該当箇所、なぜ問題か、修正案
  - 致命的：このまま進むと手戻りや不具合が確実に起きる
  - 要検討：リスクはあるが、判断次第で許容できる
  - 好みの問題：どちらでも成立する
- 確認した観点：問題がなかった観点も、何を確認したかを書く
- 判断できなかった点：情報不足で評価できなかった箇所と、何があれば判断できるか
- 根拠の見当たらない決定：成果物が決めているが、前提・参照資料・ユーザーの決定事項に根拠が見当たらない箇所

問題がなければ、無理に指摘を作らず GO と判定してよい。
```

### 6. 結果を記録する（cc-sdd の場合）
レビュー結果を `.kiro/specs/<feature>/reviews/<phase>-r<回数>.md` に保存する（例：`requirements-r1.md`）。冒頭に次を書く。

```
- 対象: requirements.md
- 対象のハッシュ: <手順1で控えた git hash-object の結果。記録を書く時点で計算し直さない>
- 日時: <ISO 8601>
- 判定: GO / 条件付きGO / NO-GO
```

続けて、レビュアーの出力と、手順7の指摘の分類を書く。
ハッシュを残すのは、「今の版の成果物がレビュー済みか」を /issue が機械的に確認できるようにするため。成果物を修正したらハッシュが変わるので、承認の前に再レビューが必要になる。

### 7. 結果の扱い（作成者側の注意）
作成者側には、指摘を退けたくなる方向のバイアスがある。次を守る。
- 各指摘を「採用／却下／ユーザー判断」に分類する。却下には必ず理由を付ける。「意図的な割り切り」なら、どの前提に基づくかを示す
- 「判断できなかった点」は、作成者側で補える事実なら補う。ユーザーが決めることと「根拠の見当たらない決定」は、cc-sdd の場合 /issue のヒアリングに回し（clarifications.md と照合して、記録されていないものを質問する）、それ以外の場合はユーザーに選択形式で質問する
- ユーザーへの提示は承認ダイアログ（AskUserQuestion）の前に行う。形式：判定、致命的・要検討の指摘とその分類、判断できなかった点
- 好みの問題は一覧にまとめて短く示すだけでよい

### 8. 再レビュー
- 修正後は、成果物の全文と前回からの差分、前回の指摘を渡す。差分と前回の指摘の解消を重点的に見るよう頼むが、差分以外の指摘も許可する（再レビューの範囲を作成者が絞ると、都合のよい切り取りになり得るため）
- 再レビューは最大2回まで。それでも致命的な指摘が残る場合は、論点をまとめてユーザーに判断を委ねる

## 比較モード（方向を決める前）
選択肢が複数あるときは、成果物レビューではなく比較を依頼する。
- どの案が推しかを伝えない。案の名前は中立なもの（A案・B案）にする
- 評価基準（コスト、保守性、戻しやすさなど）を先に出させてから、各案を当てはめさせる
- 出力：基準ごとの比較、推奨案とその理由、推奨が変わる条件

## 限界
独立したレビューでも、すべての問題を拾えるわけではない。「判断できなかった点」によって、どこが確認されていないかが見える状態にしておくことが重要。
