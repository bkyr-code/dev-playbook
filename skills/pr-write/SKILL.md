# pr-write：PR のタイトルと本文を作る

## 方針
- **読む人が30秒で「何を・なぜ・どこを見ればよいか」を掴めること**を優先する。変更したファイルの羅列はしない（差分は GitHub の画面で見られる）
- **事実だけを書く**。作成者は自分の成果を良く書きがちなので、次を守る
  - 「動作確認」には、実際に実行したことと、その結果だけを書く。実行していないことは「未確認」と書く
  - 「問題なく動作」「完璧に」のような評価語は使わない
  - 既知の制限や残課題は隠さず書く
- 該当しないセクションは、見出しごと削除する（「なし」とは書かない）。ただし「概要」「関連」「動作確認」は必須
- リポジトリに PR テンプレート（`.github/PULL_REQUEST_TEMPLATE.md`）があり、そのリポジトリの CLAUDE.md がテンプレートに従うよう指示している場合は、テンプレートの構成を優先する

## 材料を集める
- Issue：`gh issue view <番号>`（ブランチ名の先頭の数字が Issue 番号）
- Spec：`.kiro/specs/<feature>/` の requirements.md・design.md・tasks.md と `reviews/`（承認ゲートでのレビュー判定と、却下した指摘の理由）
- 差分：`git diff <既定ブランチ>...HEAD --stat` と、必要な部分の `git diff`。コミット一覧は `git log <既定ブランチ>..HEAD --oneline`
- CI とテスト：`gh pr checks`（PR 作成後）、ローカルで実行したテストのコマンドと結果

## タイトル
`<種類>: <何をしたか>`
- 種類：`feat`（機能追加）／`fix`（バグ修正）／`refactor`（挙動を変えない整理）／`docs`／`ci`／`chore`
- 何をしたか：日本語で、結果がわかる形にする。目安は40文字以内
  - 良い例：`feat: 保有株の一覧に損益率の列を追加`
  - 悪い例：`feat: 対応`、`fix: バグ修正`、`Issue #12`
- Squash merge では、このタイトルが既定ブランチのコミットメッセージになる。履歴として読める形にする

## 本文の形式

```markdown
## 概要
<!-- 何を・なぜ。1〜3行。Issue を読まなくても分かるように -->

## 関連
Closes #<Issue番号>
Spec: `.kiro/specs/<feature>/`

## 変更内容
<!-- 機能や領域のまとまりごとに箇条書き。ファイル名の羅列ではなく、何が変わったか -->
- 
- 

## 判断したこと
<!-- 設計上の主な判断と、採らなかった案。Spec のレビューで却下した指摘があれば、その理由も -->
- 

## 動作確認
<!-- 実際に実行したことと結果だけ。実行していないものは「未確認」と書く -->
- [x] CI（ci / semgrep）：通過
- [x] <実行したテストや手動確認>：<結果>
- [ ] <未確認のこと>：未確認（理由）

## 見てほしいところ
<!-- レビューで特に見てほしい箇所、リスク、既知の制限・残課題 -->
- 

## チェックリスト
- [ ] AI コードレビュー実施済み
- [ ] `docs/FEATURES.md` 更新済み（ある場合）
- [ ] `.github/workflows/` の変更なし（ある場合は「見てほしいところ」に明記）

## スクリーンショット
<!-- UI の変更がある場合のみ。Minecraft の Mod・プラグインは、ゲーム内の画面やログでもよい -->
```

- 軽量ルート（Spec なし）の場合：「関連」から Spec の行を消し、「判断したこと」に原因と直し方を書く
- Minecraft の Mod・プラグインの場合：「動作確認」に、対象の Minecraft バージョンとローダー（Fabric／NeoForge／Paper など）、ゲーム内で確認したかどうかを書く。CI でビルドした jar は PR の Artifacts からダウンロードできることも書いておく

## 作成・更新のしかた
- 本文はファイルや引数に直接書かず、標準入力で渡す（改行や記号のエスケープで崩れないようにするため）
  - 作成：`gh pr create --title "<タイトル>" --body-file - --base <既定ブランチ>`
  - 更新：`gh pr edit <番号> --body-file -`
- 作成の前に、タイトルと本文をユーザーに示して確認を取る
- PR を作ったあとに追加のコミットをした場合（レビュー対応や CI の修正）は、本文の「変更内容」「動作確認」を実態に合わせて更新する
- CI の結果は PR 作成時点では出ていないので、作成時は「CI：実行中」と書き、結果が出たら更新する

## マージ時のコミットメッセージ（Squash merge）
既定ブランチの履歴をそろえるため、マージ時に件名と本文を明示する。
- 件名：`<PR のタイトル> (#<PR番号>)`
- 本文：PR 本文の「概要」の内容（1〜3行）
- 例：`gh pr merge <番号> --squash --subject "feat: 保有株の一覧に損益率の列を追加 (#15)" --body "<概要>"`
