# issue：Issue 遂行フロー

## このスキルの位置づけ
- Issue の進め方（フェーズの順序、レビューのタイミング、コミット・PR・マージの手順）の正本はこのスキル。リポジトリの CLAUDE.md や docs/WORKFLOW.md とフローの記述が食い違う場合はこのスキルに従い、食い違いをユーザーに報告する。
- 技術ルール（コーディング規約、テスト方針、AI コードレビューのコマンドなど）はリポジトリごとに違うので、このスキルには書かない。リポジトリの CLAUDE.md と `.kiro/steering/` に従う。
- 前提：`.kiro/` があり、`gh` が使えるリポジトリ。`.kiro/` がなければ、このスキルは対象外だと伝えて止まる。
- 原則：1 Issue = 1 Spec。作業が複数の Spec に分かれる場合は、Issue を分ける。
- ユーザーに判断を求めるときは、確認・選択・承認のどれでも、AskUserQuestion の選択形式で聞く（テキストで質問を並べて自由回答を待たない）。1回に最大4問なので、多いときは複数回に分ける。
- ユーザーの依頼文に独自の手順や条件（「最初に〜を確認して」「報告したら承認を待って」など）が書かれている場合は、このスキルの手順に加えてそれも守る。両者が衝突する場合は、進める前に止まってどちらに従うか確認する。

## ユーザーに入力してもらうコマンド
`/kiro-discovery` と `/kiro-impl` は、モデルからは呼び出せない設定になっている。これらが必要な場面では、実行せずに「`/kiro-impl <feature>` を入力してください。終わったら `/issue` を呼び直してください」とユーザーに依頼する。

## 毎回最初にやること：現在地の判定
このスキルは長い作業の途中で呼び直される前提で作っている。呼ばれたら、まず次を確認して現在地を判定する。会話の記憶より、ファイルと git の状態を優先する。

1. 既定ブランチ：`gh repo view --json defaultBranchRef --jq .defaultBranchRef.name`。失敗したら `git symbolic-ref refs/remotes/origin/HEAD`。main とは限らない
2. 未コミットの変更：`git status --porcelain`
3. 現在のブランチと Issue 番号：`gh issue develop` が作るブランチ名は `<番号>-...` なので、先頭の数字が Issue 番号。引数で Issue 番号が渡された場合は、`gh issue develop --list <番号>` で紐付いたブランチを探し、あれば checkout する
4. Issue 本文：`gh issue view <番号>`。ルート（通常／軽量）と `Spec: .kiro/specs/<feature>/` を読む
5. Spec の状態：`spec.json` の `approvals.*.generated` と `approvals.*.approved`、`tasks.md` のチェック状況と `_Blocked:_` の有無、`reviews/` 配下のレビュー記録、`clarifications.md`（ヒアリングの記録。各フェーズの「生成前」「生成後」節の状態と、未回答・未反映の項目）
6. PR の状態：`gh pr view --json state,url`
7. CI の有無：`git ls-files .github/workflows`。コミットされたワークフローがなければ、`/ci-setup` で CI とブランチ保護を入れることを1回だけ提案する。Issue の作業はそのまま続けてよい

判定には、下の表を**上から順に**当てはめ、最初に一致した行を現在地とする。ファイルの有無ではなく、spec.json のフラグで判定する（`/kiro-spec-init` の時点で中身のない requirements.md が作られるため）。

| 順 | 状態 | 現在地 |
|---|---|---|
| 1 | PR がマージ済み | 完了。後片付けだけ確認する |
| 2 | PR がクローズ済み（マージなし） | 止まって、Issue を続けるか閉じるかユーザーに聞く |
| 3 | PR がオープン | フェーズ6 |
| 4 | 既定ブランチ上にいる | 引数や依頼文で既存の Issue が指定されていれば、フェーズ0-A（Issue の確認）。指定がなければフェーズ0。Issue に紐付いたブランチがあれば、checkout してから判定し直す |
| 5 | Issue 本文のルートが軽量 | 軽量ルート（フェーズ4の末尾）。作業の進み具合は git の差分とテストの状態で判断する |
| 6 | spec.json がない | フェーズ3の手順1（spec-init） |
| 7 | `approvals.requirements.approved` が false | `generated` が false なら、clarifications.md の「requirements / 生成前」節が「完了」かどうかで、生成前ヒアリングか要件の生成かを決める。true なら、「生成後」節が「完了」で未回答・未反映の項目がなければ承認ゲート、そうでなければ生成後ヒアリング |
| 8 | `approvals.design.approved` が false | 7 と同じ判定を design について行う |
| 9 | `approvals.tasks.approved` が false | タスクの生成、またはタスクの承認ゲート |
| 10 | `tasks.md` に `_Blocked:_` が残っている | 止まって、ブロックの理由を示し、Spec を見直すか、ユーザーの判断を仰ぐ |
| 11 | `tasks.md` に未完了のタスクがある | フェーズ4 |
| 12 | それ以外（タスクがすべて完了） | フェーズ5 |

判定した現在地を「現在地：フェーズ○（理由）→ 次にやること」と1〜2行で示してから進める。

## セッション名
対象の Issue が決まったら（フェーズ0-A の開始時、フェーズ2で Issue を作った直後、Issue のブランチで再開したとき）、このセッションの名前を `#<Issue番号> <要約>` の形式にそろえる。例：`#2 導入検証`
- 要約：Issue タイトルから、何をする Issue かが分かる部分を20文字以内で抜き出す。`[01]` のような番号付けや「フェーズ1：」のような前置きは省く
- 変え方：セッション名を変える道具が使える環境（デスクトップアプリの Code タブなど）では、自分で変える。使えない環境では、`/rename #2 導入検証` を示して、ユーザーに入力してもらう
- Issue のブランチがある場合は、`git config branch.<ブランチ名>.sessionTitle "#2 導入検証"` で名前を記録する。PC の Claude Code では、セッションの開始・再開時にフックがこの名前を読んで、自動でセッション名を付ける
- 既にこの名前になっていれば、何もしない

## フェーズ0-A：既存 Issue の確認（既存の Issue から始める場合）
Issue に書かれた内容をそのまま正しいと見なして進めない。Issue を書いたのが過去の自分や Claude でも、目的や範囲がずれていたり、リポジトリの現状と合っていなかったりすることがある。

1. 材料を集める：`gh issue view <番号> --comments`（本文・コメント・ラベル）、リポジトリの README と `.kiro/steering/`、関連しそうなコードと既存の Spec、ほかのオープンな Issue（`gh issue list`）
2. `spec-review` スキルで、Issue 本文を独立レビューにかける（対象の種類は「Issue」）。Issue を書いた側の見方を持ち込まないため。見る観点は次のとおり
   - 目的（誰の何が、どう変わるか）が明確か
   - やること・やらないこと（範囲）がはっきりしているか
   - 完了条件が検証できる形で書かれているか
   - リポジトリの現状と食い違っていないか（既に実装済み、前提の機能やファイルがない、技術的に成り立たない など）
   - ほかの Issue と重複・衝突していないか
   - 1つの Spec に収まる大きさか（大きすぎるなら分割案）
   - 要件の段階で決める必要がある点（ここでは質問せず、申し送り用に列挙するだけ）
3. 結果を報告する：判定、重要度（致命的／要検討／好みの問題）付きの問題点、Issue 本文の修正案（変更前と変更後）
   - **このフェーズで質問するのは、Issue レベルの問題だけ**：目的、範囲（やる・やらない）、完了条件、大きさ（分割するか）、コードの現状やほかの Issue との食い違い。これらのうちユーザーが決めることは、「ヒアリング」節のやり方で質問し、回答を修正案に反映してから手順4に進む（承認の選択とは別に聞く）
   - 要件レベルの不明点（画面の挙動、異常時の扱い、データの細部、技術的な選択など）は、ここでは質問しない。Issue 本文の修正案に「## 要件で決めること」として箇条書きで申し送り、フェーズ3の要件の生成前ヒアリングで聞く
4. **ここで止まり、ユーザーの承認を待つ**。AskUserQuestion で「このまま進める」「Issue を修正してから進める」「止める（Issue を見直す）」を選んでもらう
5. 「修正してから進める」なら、修正後の本文を示して確認を取り、`gh issue edit <番号> --body-file -` で更新する
6. フェーズ0に進む。種類はラベル（`enhancement`／`bug`／`refactor`）から判断し、確認だけ取る

この確認は、Issue のブランチを作る前に1回だけ行う。ブランチが既にある（作業を再開している）場合は行わない。

## フェーズ0：種類とルートを決める
1. 種類を AskUserQuestion で確認する：機能追加／バグ修正／リファクタリング
2. 既存の Spec を更新する作業か、新しい Spec を作る作業かを確認する
3. ルートを決める
   - **通常ルート**（Spec を書く）：機能追加、挙動が変わる変更、複数のモジュールにまたがる変更、データ構造や外部インターフェースが変わる変更
   - **軽量ルート**（Spec を書かない）：原因と直し方が明確なバグ修正、挙動を変えない小さなリファクタ。目安は数ファイル以内で、データ構造と外部インターフェースが変わらないこと
   - ルートに迷う機能追加は、ユーザーに `/kiro-discovery "<説明>"` の入力を依頼して判定してもらう。「Spec 不要」なら軽量ルート、「複数 Spec に分ける」なら Issue を分ける
4. 選んだルートと理由を1行で示し、AskUserQuestion で確認する

## フェーズ1：Discovery（対話で方向を決める）
- 目的、やること、やらないこと、制約を会話で詰める。この段階では、自分から MD ファイルを作らない
  - 例外：`/kiro-discovery` が作る `.kiro/specs/<feature>/brief.md`。既定ブランチ上ではコミットせず、フェーズ2でブランチに持ち越す
- 方向に複数の選択肢がある場合は、`spec-review` の比較モードで評価してから決める。どれを推しているかはレビュアーに伝えない
- 新しい Spec を作る場合は、フィーチャー名（ケバブケース）をここで決める。brief.md があれば、そのディレクトリ名を使う
- 終わったら、決まった内容を5〜10行にまとめて示す。これが Issue 本文になる

## フェーズ2：Issue とブランチ
1. 未コミットの変更があれば（brief.md を除く）、止まってユーザーに扱いを聞く
2. 既定ブランチを最新にする：`git checkout <既定>` → `git pull`
3. Issue がまだなければ作る：`gh issue create --title ... --body ... --label <enhancement|bug|refactor>`
   - 本文には、フェーズ1のまとめ（要約しない原文）、ルート（通常／軽量）、通常ルートなら `Spec: .kiro/specs/<feature>/` と「新規／既存 Spec の更新」の区別を書く
4. ブランチを作る：`gh issue develop <番号> --checkout`。Issue に紐付いたブランチが既にあれば、それを checkout する
5. 以降の作業は、すべてこのブランチ上で行う

## フェーズ3：Spec（通常ルートのみ）
`/kiro-spec-quick` と `--auto`、`-y` は使わない。承認ゲートを飛ばしてしまうため。ユーザーが明示的に省略を指示した場合だけ使い、その理由を `reviews/` に記録する。

1. **入口**
   - 新しい Spec：`/kiro-spec-init` を、フェーズ1で決めたフィーチャー名を指定して実行する。名前の衝突で別名（`-2` 付きなど）になった場合は、`gh issue edit` で Issue 本文の Spec パスを直す
   - 既存 Spec の更新：spec.json の `approvals.*.approved` をすべて false に、`ready_for_implementation` を false にしてから、要件の生成に進む。そうしないと、kiro の各コマンドが承認済みと見なし、承認ゲートを通らずに先へ進んでしまう
   - `/kiro-spec-init` が質問した場合は、その質問と回答も clarifications.md に記録する
2. **要件の生成前ヒアリング**（「ヒアリング」節）。Issue 本文に「要件で決めること」があれば、それを必ず質問の対象に含める
3. clarifications.md を読み込んでから `/kiro-spec-requirements <feature>` を実行する。kiro が生成後に「要件がすべてを網羅しているか」を尋ねる手順は、ユーザーにそのまま出さず、承認ゲートで扱う
4. **要件の生成後ヒアリング** → **承認ゲート（要件）**
5. 既存のコードがある場合は `/kiro-validate-gap <feature>` を実行する（任意。設計の前提を確認するため）
6. **設計の生成前ヒアリング**：技術的な選択（ライブラリ、構成、データ構造、外部インターフェース、互換性、データ移行など）を含め、設計で決めることを聞く。`/kiro-spec-design` は自分ではユーザーに質問しないため、ここで先に決めておく
7. clarifications.md を読み込んでから `/kiro-spec-design <feature>` を実行する
8. **設計の生成後ヒアリング**：research.md の Design Decisions と design.md のうち、回答に根拠のない選択をすべて質問にする → **承認ゲート（設計）**
9. `/kiro-spec-tasks <feature>` → **承認ゲート（タスク）**
   - `/kiro-spec-tasks` は生成直後に自分で承認を尋ねる。この質問はユーザーにそのまま出さず、「承認は issue の承認ゲートで行う」と伝えて false のままにする。true になってしまっていたら、false に戻してから承認ゲートに入る
   - タスクの段階で決まっていないことが見つかったら、それは設計の穴なので、差し戻しのルールで設計に戻ってヒアリングする
10. `docs/FEATURES.md` があれば、機能の行を追加する（ステータス：🚧 開発中、作成日：今日）。この変更は、タスクの承認ゲート後のコミットに含める

### ヒアリング（要件・設計で共通）
要件・設計を AI の推測で埋めないための手順。**少しでも決まっていないことは、すべてユーザーに質問する**。後から安く直せることも、技術的な選択（ライブラリ、構成など）も対象にする。質問数に上限は設けない。記録先は `.kiro/specs/<feature>/clarifications.md`（形式は下）。

1. **洗い出す**：要件・設計の文書に書くことになる決定のうち、Issue 本文・clarifications.md の回答・steering・上流の成果物に根拠がないものをすべて挙げる。生成後のヒアリングでは、成果物の記述と research.md の判断のうち、根拠がないものを挙げる
   - 対象外：要件・設計の文書に書かない実装の細部（変数名、ファイル内の書き方など）
2. **調べられる事実は調べる**：コード、ドキュメント、ライブラリの仕様などで確定する事実は、聞かずに調べる。調べて分かった事実で選択肢が絞られる場合も、選ぶのはユーザー
3. **照合する**：同じ論点が clarifications.md か Issue 本文で既に決まっていれば、聞き直さない
4. **聞く**：AskUserQuestion の選択形式で、1回に4問まで、影響の大きい順に聞く。多ければ回数を分けて、残りがなくなるまで続ける。ある回答で前提が変わる質問は、その回答の後に回す
   - 「〜でよいですか」とは聞かず、比べられる選択肢（2〜4択）から選んでもらう。各選択肢の説明には、選んだ結果と代償を同じ詳しさで書く
   - 各質問に、なぜ決める必要があるか（どこに効くか）を1行で添える
   - 技術的な選択には、推奨を付けてよい。付ける場合は、推奨の選択肢の先頭に置いて「（推奨）」と書き、根拠と「推奨が変わる条件」を説明に書く。好みや方針で決まる選択には推奨を付けない
   - 正当な場合は、「今回は範囲外にする」「後で決める」も選択肢に入れる
   - すべての質問に、最後の選択肢として「よくわからない・詳しく説明してほしい」を入れる（選択肢は最大4つなので、実質的な選択肢は3つまでになる。4つ以上の案がある場合は、質問を分けるか、近い案をまとめる）。これが選ばれたら、背景、各選択肢の意味と具体例、選んだ場合の影響を平易に説明してから、同じ質問をもう一度聞く
5. **記録する**：回答を受けたら、ほかの作業より先に clarifications.md に書く。回答は原文で残し、自由記述を解釈したときは「解釈」と明記する。回答が Issue・steering・ほかの回答と矛盾していれば、そのまま受け入れず、重要度を付けて指摘する。回答で目的・範囲・完了条件が変わる場合は、Issue 本文の修正案を示し、差し戻しのルールに従う
6. **反映を確認する**：成果物を生成・修正したら、回答済みの各項目の「反映先」を成果物と照合し、反映されていなければ直す
7. 質問がなかった場合も、節に「完了（質問なし：理由）」と書く（現在地の判定に使う）

- kiro の各コマンドが実行中に自分で質問する場合も、同じやり方で聞いて記録する
- 差し戻すときは、そのフェーズより後の回答を「要再確認」にし、次のヒアリングで、上流の変更後も有効かを確認する
- ヒアリングは独立レビューの前に終える。レビュー後に聞いて成果物が変わると、再レビューが必要になるため。承認ゲートで新たに出た不明点は、承認ダイアログとは別に聞く

clarifications.md の形式：

```markdown
# Clarifications: <feature>
<!-- /issue が管理する。spec-review には「回答済み」「反映済み」の項目の「質問」と「回答（原文）」だけを渡す -->

## requirements / 生成前
- 状態: 完了（質問 3 件）   <!-- 進行中 / 完了 / 完了（質問なし：理由） -->

### C1
- 状態: 反映済み   <!-- 未回答 / 回答済み（未反映） / 反映済み / 範囲外 / 要再確認 -->
- 出どころ: 生成前の洗い出し   <!-- kiro 実行中の質問 / 生成後の洗い出し / レビュー（requirements-r1） -->
- 質問: …
- 示した選択肢: A …／B …／C …
- 回答（原文）: …
- 決定: …（自由記述を解釈した場合は「解釈」と明記）
- 反映先: requirements.md 2.3, 3.1
```

### 承認ゲート（各フェーズ共通）
承認ダイアログを出す前に、次をこの順で必ず行う。

1. **独立レビュー**：`spec-review` スキルで、今の版の成果物をレビューする。結果は `.kiro/specs/<feature>/reviews/<phase>-r<回数>.md` に、レビュー時点の成果物のハッシュとともに記録される
2. **指摘への対応**：指摘を採用して成果物を直したら（重要度を問わず）、手順1に戻って再レビューする。再レビューは最大2回まで。それでも致命的な指摘が残る場合は、論点をまとめてユーザーに判断を委ねる
   - レビューの「判断できなかった点」と「根拠の見当たらない決定」は、clarifications.md と照合し、記録されていないものはすべて「ヒアリング」節のやり方で質問する。回答で成果物を直したら、手順1に戻る
3. **ユーザーへの提示**：次を箇条書きで示す
   - 重要な決定事項
   - ヒアリングで決まった事項と、その反映先
   - 影響範囲
   - 未決事項（ヒアリングで「後で決める」になったものを含む）
   - レビューの判定と、致命的・要検討の指摘およびその分類（採用／却下と理由／ユーザー判断）
   - レビュアーが判断できなかった点
4. **レビュー済みの確認**：承認ダイアログを出す直前に、最新のレビュー記録にある「対象のハッシュ」と、今の成果物の `git hash-object` が一致することを確認する。一致しなければ、提示中に成果物が変わっているので、手順1に戻る
5. **承認ダイアログ**：AskUserQuestion で「承認して次へ」「修正して再レビュー」「前のフェーズに戻る」を選んでもらう。承認ダイアログには、ほかの質問を一緒に入れない
6. **承認の記録**：「承認して次へ」が選ばれたら、もう一度ハッシュの一致を確認してから、`spec.json` の `approvals.<phase>.approved` を true にし、`updated_at` を更新する。タスクの承認時は `ready_for_implementation` も true にする
7. **コミット**：そのフェーズの成果物と `reviews/`・`clarifications.md`（とタスク承認時は `docs/FEATURES.md`）をコミットする案を示し、ユーザーの確認を取ってからブランチにコミットする。フェーズをまたいでファイルを未コミットのまま残さないため

**差し戻しのルール**：あるフェーズに戻るとき（ユーザーが承認後に変更を求めた場合や、実装中に Spec を直す場合）は、そのフェーズ**以降すべて**の `approvals.*.approved` と `ready_for_implementation` を false にする。下流の成果物は、上流の変更に合わせて作り直すか見直したうえで、承認ゲートをやり直す。

## フェーズ4：実装
1. ユーザーに `/kiro-impl <feature>` の入力を依頼する（タスク番号を付ければ手動モード）
   - `/kiro-impl` はタスクごとにブランチへ自動でコミットする。依頼の前に、そのことを示して AskUserQuestion で確認を取る。その確認をもって、実装中の各コミットを許可されたものとみなす。push は別に確認する
   - 自動モードの `/kiro-impl` は、最後に `/kiro-validate-impl` まで実行する。手動モードで全タスクを終えた場合だけ、`/kiro-validate-impl <feature>` を別に実行する
2. 実装中に Spec と食い違う事実が見つかったら、黙って実装で吸収しない。どの Spec のどの記述と食い違うかを示し、Spec を直すか（直す場合は差し戻しのルールに従う）、実装を合わせるかをユーザーに確認する
3. `/kiro-impl` が終わったら `/issue` を呼び直してもらい、現在地を判定する

**軽量ルートの場合**：原因を特定する（必要なら `kiro-debug`）→ 再現テストを書く → 修正する → テストが通ることを確認する。修正方針に複数の選択肢がある場合や、戻しにくい変更を含む場合は、`spec-review` にかける。決まっていないことは「ヒアリング」節のやり方で質問する。どちらも記録先は Issue のコメント（`gh issue comment`）とする。

## フェーズ5：コミットと PR
1. リポジトリのルールにある AI コードレビュー（例：`/code-review`）を実行し、指摘を直す。同じ指摘が2回続けて解消しない場合や、指摘の採否に迷う場合は、ユーザーに判断を委ねる
2. `docs/FEATURES.md` があれば、該当行のステータスを ✅ 実装済みにし、完了日を記入する。マージ後に既定ブランチで直接更新すると既定ブランチへの直接コミットになるため、PR に含めて更新する
3. コミット案を示し、ユーザーの確認を取ってからコミットする
4. ユーザーの確認を取ってから `git push` する
5. PR を作る：`pr-write` スキルで、決まった形式のタイトルと本文を作り、ユーザーの確認を取ってから作成する。以降、追加のコミットや CI の結果に合わせて本文を更新する
6. `gh pr checks --watch` で CI が終わるのを待って結果を確認する。失敗していたら修正する。修正のたびに push の確認が要るので、直す内容をまとめてから一度に確認を取る。同じ失敗を2回直せなかったら、ユーザーに判断を委ねる
   - CI がないリポジトリでは、型チェック・lint・テストのうちリポジトリにあるものをローカルで実行し、結果を PR 本文に書く

## フェーズ6：マージ
1. CI が通っていることと、PR テンプレートのチェック項目が満たされていることを確認する。CI が失敗している PR はマージしない（ブランチ保護があれば GitHub 側でも止まる）
   - PR が `.github/workflows/` を変更している場合は、マージの確認を取るときに、その変更内容を必ず明示する。必須チェックは名前で照合されるため、ワークフローを書き換えると CI を実質的に素通りできてしまうから
2. ユーザーの確認を取ってから Squash merge する。コミットの件名と本文は `pr-write` の「マージ時のコミットメッセージ」に従って明示する（`gh pr merge <番号> --squash --subject ... --body ...`）
3. 既定ブランチに戻って `git pull` し、Issue が閉じていることを確認する
4. 後片付け：マージ済みのローカルブランチとリモートブランチを削除するか、ユーザーに確認してから削除する

## 全フェーズ共通のルール
- コミット・push・マージは、必ずユーザーの確認を取ってから行う（`/kiro-impl` のタスクごとのコミットは、フェーズ4の確認で許可済みとする）
- コミットの直前には毎回、現在のブランチが既定ブランチでないことを確認する
- 途中で範囲が変わったら、影響する最も上流のフェーズに戻る（差し戻しのルールに従う）
- フェーズを終えるたびに、現在地と次にやることを1〜2行で示す
- 作業中に見つけた別件（別のバグ、別のリファクタ）は、その場で直さずに別 Issue の候補として報告する。ただし、今の Issue の作業に必要なリファクタは、この Issue の中で行ってよい
