# issue：Issue 遂行フロー

## このスキルの位置づけ
- Issue の進め方（フェーズの順序、レビューのタイミング、コミット・PR・マージの手順）の正本はこのスキル。リポジトリの CLAUDE.md や docs/WORKFLOW.md とフローの記述が食い違う場合はこのスキルに従い、食い違いをユーザーに報告する。
- 技術ルール（コーディング規約、テスト方針、AI コードレビューのコマンドなど）はリポジトリごとに違うので、このスキルには書かない。リポジトリの CLAUDE.md と `.kiro/steering/` に従う。
- 前提：`.kiro/` があり、`gh` が使えるリポジトリ。`.kiro/` がなければ、このスキルは対象外だと伝えて止まる。
- 原則：1 Issue = 1 Spec。作業が複数の Spec に分かれる場合は、Issue を分ける。

## ユーザーに入力してもらうコマンド
`/kiro-discovery` と `/kiro-impl` は、モデルからは呼び出せない設定になっている。これらが必要な場面では、実行せずに「`/kiro-impl <feature>` を入力してください。終わったら `/issue` を呼び直してください」とユーザーに依頼する。

## 毎回最初にやること：現在地の判定
このスキルは長い作業の途中で呼び直される前提で作っている。呼ばれたら、まず次を確認して現在地を判定する。会話の記憶より、ファイルと git の状態を優先する。

1. 既定ブランチ：`gh repo view --json defaultBranchRef --jq .defaultBranchRef.name`。失敗したら `git symbolic-ref refs/remotes/origin/HEAD`。main とは限らない
2. 未コミットの変更：`git status --porcelain`
3. 現在のブランチと Issue 番号：`gh issue develop` が作るブランチ名は `<番号>-...` なので、先頭の数字が Issue 番号。引数で Issue 番号が渡された場合は、`gh issue develop --list <番号>` で紐付いたブランチを探し、あれば checkout する
4. Issue 本文：`gh issue view <番号>`。ルート（通常／軽量）と `Spec: .kiro/specs/<feature>/` を読む
5. Spec の状態：`spec.json` の `approvals.*.generated` と `approvals.*.approved`、`tasks.md` のチェック状況と `_Blocked:_` の有無、`reviews/` 配下のレビュー記録
6. PR の状態：`gh pr view --json state,url`

判定には、下の表を**上から順に**当てはめ、最初に一致した行を現在地とする。ファイルの有無ではなく、spec.json のフラグで判定する（`/kiro-spec-init` の時点で中身のない requirements.md が作られるため）。

| 順 | 状態 | 現在地 |
|---|---|---|
| 1 | PR がマージ済み | 完了。後片付けだけ確認する |
| 2 | PR がクローズ済み（マージなし） | 止まって、Issue を続けるか閉じるかユーザーに聞く |
| 3 | PR がオープン | フェーズ6 |
| 4 | 既定ブランチ上にいる | フェーズ0（引数の Issue にブランチがあれば、checkout してから判定し直す） |
| 5 | Issue 本文のルートが軽量 | 軽量ルート（フェーズ4の末尾）。作業の進み具合は git の差分とテストの状態で判断する |
| 6 | spec.json がない | フェーズ3の手順1（spec-init） |
| 7 | `approvals.requirements.approved` が false | 要件の生成、または要件の承認ゲート（`generated` で区別） |
| 8 | `approvals.design.approved` が false | 設計の生成、または設計の承認ゲート |
| 9 | `approvals.tasks.approved` が false | タスクの生成、またはタスクの承認ゲート |
| 10 | `tasks.md` に `_Blocked:_` が残っている | 止まって、ブロックの理由を示し、Spec を見直すか、ユーザーの判断を仰ぐ |
| 11 | `tasks.md` に未完了のタスクがある | フェーズ4 |
| 12 | それ以外（タスクがすべて完了） | フェーズ5 |

判定した現在地を「現在地：フェーズ○（理由）→ 次にやること」と1〜2行で示してから進める。

## フェーズ0：種類とルートを決める
1. 種類を AskUserQuestion で確認する：機能追加／バグ修正／リファクタリング
2. 既存の Spec を更新する作業か、新しい Spec を作る作業かを確認する
3. ルートを決める
   - **通常ルート**（Spec を書く）：機能追加、挙動が変わる変更、複数のモジュールにまたがる変更、データ構造や外部インターフェースが変わる変更
   - **軽量ルート**（Spec を書かない）：原因と直し方が明確なバグ修正、挙動を変えない小さなリファクタ。目安は数ファイル以内で、データ構造と外部インターフェースが変わらないこと
   - ルートに迷う機能追加は、ユーザーに `/kiro-discovery "<説明>"` の入力を依頼して判定してもらう。「Spec 不要」なら軽量ルート、「複数 Spec に分ける」なら Issue を分ける
4. 選んだルートと理由を1行で示し、AskUserQuestion で確認する

## フェーズ1：Discovery（対話で方向を決める）
- 目的、やること、やらないこと、制約を会話で詰める。この段階では、自分から MD ファイルを作らない
  - 例外：`/kiro-discovery` が作る `.kiro/specs/<feature>/brief.md`。既定ブランチ上ではコミットせず、フェーズ2でブランチに持ち越す
- 方向に複数の選択肢がある場合は、`spec-review` の比較モードで評価してから決める。どれを推しているかはレビュアーに伝えない
- 新しい Spec を作る場合は、フィーチャー名（ケバブケース）をここで決める。brief.md があれば、そのディレクトリ名を使う
- 終わったら、決まった内容を5〜10行にまとめて示す。これが Issue 本文になる

## フェーズ2：Issue とブランチ
1. 未コミットの変更があれば（brief.md を除く）、止まってユーザーに扱いを聞く
2. 既定ブランチを最新にする：`git checkout <既定>` → `git pull`
3. Issue がまだなければ作る：`gh issue create --title ... --body ... --label <enhancement|bug|refactor>`
   - 本文には、フェーズ1のまとめ（要約しない原文）、ルート（通常／軽量）、通常ルートなら `Spec: .kiro/specs/<feature>/` と「新規／既存 Spec の更新」の区別を書く
4. ブランチを作る：`gh issue develop <番号> --checkout`。Issue に紐付いたブランチが既にあれば、それを checkout する
5. 以降の作業は、すべてこのブランチ上で行う

## フェーズ3：Spec（通常ルートのみ）
`/kiro-spec-quick` と `--auto`、`-y` は使わない。承認ゲートを飛ばしてしまうため。ユーザーが明示的に省略を指示した場合だけ使い、その理由を `reviews/` に記録する。

1. **入口**
   - 新しい Spec：`/kiro-spec-init` を、フェーズ1で決めたフィーチャー名を指定して実行する。名前の衝突で別名（`-2` 付きなど）になった場合は、`gh issue edit` で Issue 本文の Spec パスを直す
   - 既存 Spec の更新：spec.json の `approvals.*.approved` をすべて false に、`ready_for_implementation` を false にしてから、要件の生成に進む。そうしないと、kiro の各コマンドが承認済みと見なし、承認ゲートを通らずに先へ進んでしまう
2. `/kiro-spec-requirements <feature>` → **承認ゲート（要件）**
3. 既存のコードがある場合は `/kiro-validate-gap <feature>` を実行する（任意。設計の前提を確認するため）
4. `/kiro-spec-design <feature>` → **承認ゲート（設計）**
5. `/kiro-spec-tasks <feature>` → **承認ゲート（タスク）**
   - `/kiro-spec-tasks` は生成直後に自分で承認を尋ねる。この質問はユーザーにそのまま出さず、「承認は issue の承認ゲートで行う」と伝えて false のままにする。true になってしまっていたら、false に戻してから承認ゲートに入る
6. `docs/FEATURES.md` があれば、機能の行を追加する（ステータス：🚧 開発中、作成日：今日）。この変更は、タスクの承認ゲート後のコミットに含める

### 承認ゲート（各フェーズ共通）
承認ダイアログを出す前に、次をこの順で必ず行う。

1. **独立レビュー**：`spec-review` スキルで、今の版の成果物をレビューする。結果は `.kiro/specs/<feature>/reviews/<phase>-r<回数>.md` に、レビュー時点の成果物のハッシュとともに記録される
2. **指摘への対応**：指摘を採用して成果物を直したら（重要度を問わず）、手順1に戻って再レビューする。再レビューは最大2回まで。それでも致命的な指摘が残る場合は、論点をまとめてユーザーに判断を委ねる
3. **ユーザーへの提示**：次を箇条書きで示す
   - 重要な決定事項
   - 影響範囲
   - 未決事項
   - レビューの判定と、致命的・要検討の指摘およびその分類（採用／却下と理由／ユーザー判断）
   - レビュアーが判断できなかった点
4. **レビュー済みの確認**：承認ダイアログを出す直前に、最新のレビュー記録にある「対象のハッシュ」と、今の成果物の `git hash-object` が一致することを確認する。一致しなければ、提示中に成果物が変わっているので、手順1に戻る
5. **承認ダイアログ**：AskUserQuestion で「承認して次へ」「修正して再レビュー」「前のフェーズに戻る」を選んでもらう
6. **承認の記録**：「承認して次へ」が選ばれたら、もう一度ハッシュの一致を確認してから、`spec.json` の `approvals.<phase>.approved` を true にし、`updated_at` を更新する。タスクの承認時は `ready_for_implementation` も true にする
7. **コミット**：そのフェーズの成果物と `reviews/`（とタスク承認時は `docs/FEATURES.md`）をコミットする案を示し、ユーザーの確認を取ってからブランチにコミットする。フェーズをまたいでファイルを未コミットのまま残さないため

**差し戻しのルール**：あるフェーズに戻るとき（ユーザーが承認後に変更を求めた場合や、実装中に Spec を直す場合）は、そのフェーズ**以降すべて**の `approvals.*.approved` と `ready_for_implementation` を false にする。下流の成果物は、上流の変更に合わせて作り直すか見直したうえで、承認ゲートをやり直す。

## フェーズ4：実装
1. ユーザーに `/kiro-impl <feature>` の入力を依頼する（タスク番号を付ければ手動モード）
   - `/kiro-impl` はタスクごとにブランチへ自動でコミットする。依頼の前に、そのことを示して AskUserQuestion で確認を取る。その確認をもって、実装中の各コミットを許可されたものとみなす。push は別に確認する
   - 自動モードの `/kiro-impl` は、最後に `/kiro-validate-impl` まで実行する。手動モードで全タスクを終えた場合だけ、`/kiro-validate-impl <feature>` を別に実行する
2. 実装中に Spec と食い違う事実が見つかったら、黙って実装で吸収しない。どの Spec のどの記述と食い違うかを示し、Spec を直すか（直す場合は差し戻しのルールに従う）、実装を合わせるかをユーザーに確認する
3. `/kiro-impl` が終わったら `/issue` を呼び直してもらい、現在地を判定する

**軽量ルートの場合**：原因を特定する（必要なら `kiro-debug`）→ 再現テストを書く → 修正する → テストが通ることを確認する。修正方針に複数の選択肢がある場合や、戻しにくい変更を含む場合は、`spec-review` にかける。その場合の記録先は Issue のコメント（`gh issue comment`）とする。

## フェーズ5：コミットと PR
1. リポジトリのルールにある AI コードレビュー（例：`/code-review`）を実行し、指摘を直す。同じ指摘が2回続けて解消しない場合や、指摘の採否に迷う場合は、ユーザーに判断を委ねる
2. `docs/FEATURES.md` があれば、該当行のステータスを ✅ 実装済みにし、完了日を記入する。マージ後に既定ブランチで直接更新すると既定ブランチへの直接コミットになるため、PR に含めて更新する
3. コミット案を示し、ユーザーの確認を取ってからコミットする
4. ユーザーの確認を取ってから `git push` する
5. PR を作る：`gh pr create`。本文には `Closes #<Issue番号>` と Spec のパスを書く。PR テンプレートがあればそれに従う
6. `gh pr checks --watch` で CI が終わるのを待って結果を確認する。失敗していたら修正する。修正のたびに push の確認が要るので、直す内容をまとめてから一度に確認を取る。同じ失敗を2回直せなかったら、ユーザーに判断を委ねる

## フェーズ6：マージ
1. CI が通っていることと、PR テンプレートのチェック項目が満たされていることを確認する
2. ユーザーの確認を取ってから `gh pr merge <番号> --squash` を実行する
3. 既定ブランチに戻って `git pull` し、Issue が閉じていることを確認する
4. 後片付け：マージ済みのローカルブランチとリモートブランチを削除するか、ユーザーに確認してから削除する

## 全フェーズ共通のルール
- コミット・push・マージは、必ずユーザーの確認を取ってから行う（`/kiro-impl` のタスクごとのコミットは、フェーズ4の確認で許可済みとする）
- コミットの直前には毎回、現在のブランチが既定ブランチでないことを確認する
- 途中で範囲が変わったら、影響する最も上流のフェーズに戻る（差し戻しのルールに従う）
- フェーズを終えるたびに、現在地と次にやることを1〜2行で示す
- 作業中に見つけた別件（別のバグ、別のリファクタ）は、その場で直さずに別 Issue の候補として報告する。ただし、今の Issue の作業に必要なリファクタは、この Issue の中で行ってよい
